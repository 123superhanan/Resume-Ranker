

TL;DR (What you’ll build)
Parse messy resume PDFs → produce clean, structured text
Chunk text into meaningful units (skills, job entries, projects)
Embed chunks with a semantic model and store them in a vector DB
On a Job Description (JD): filter, retrieve top chunks, re-rank with a cross-encoder, aggregate to resume level, present explainable results
1) Ingestion & parsing — turn PDFs into structured text
What to do, and why it matters

Real resumes are inconsistent: multi-column layouts, icons, tables, and scanned images. If you lose section boundaries or mix columns, chunking and embeddings suffer. The goal at this stage is to get clean text and section hints (headings like EXPERIENCE, SKILLS, PROJECTS).

Tools (click to docs)

pdfplumber — reliable PDF text extraction. (https://github.com/jsvine/pdfplumber)
PyMuPDF — fast, robust page handling for large pipelines. (https://pymupdf.readthedocs.io/)
unstructured.io — higher-level layout parsing for multi-column and mixed content. (https://unstructured-io.github.io/unstructured/)
Tesseract OCR — OCR for scanned PDFs when needed. (https://github.com/tesseract-ocr/tesseract)
Details / best practices

Attempt native text extraction first (pdfplumber / PyMuPDF).
If page appears as image or extraction fails, run OCR (Tesseract) and then clean text.
Preserve headings and bullets; normalize whitespace and remove headers/footers when possible.
Extract candidate metadata when available (name, email, location) and a best-effort skill list (use simple NER or regex heuristics).
Alternatives & tradeoffs

Quick-and-dirty: plain text extraction — fast but fragile.
Robust: unstructured.io — better layout parsing but heavier to run.
If you only accept DOCX, parsing is easier — but real world resumes are mostly PDF.
2) Chunking — the single most impactful step
What to do, and why

Instead of slicing every N tokens, use structure-aware chunking: whole skill lists as one chunk, one job/experience per chunk (role + company + bullets), one project/cert per chunk. Embeddings perform best on coherent semantic units — you will get far more accurate retrieval vs blind token chopping.

Recommended chunk rules

Skills: keep as single chunk so skill matching is precise.
Experience: one chunk per job entry (role + company + bullets).
Projects / Certifications: one chunk per entry.
Education: whole block as one chunk.
If a single chunk > ~800 tokens, split logically (role summary / responsibilities / achievements), not arbitrarily.
Why structure-aware beats token windows

Preserves meaning: a whole job entry often contains the exact evidence a JD needs
Reduces noisy matches from mixed contexts (e.g., separating skills list from achievements).
Facilitates metadata tagging (company, dates) for filtering and ranking.
Fallbacks

Token-based chunking (500 tokens + overlap) is a simple fallback but yields noisier matches.
Sliding windows increase recall but multiply vectors and compute costs.
3) Embeddings — convert chunks into vectors
What to do, and why

Embeddings turn text into numeric vectors so similar content is nearby in vector space. Choose a model that understands technical and professional language (skills, seniority, role context).

Recommended open-source model family

BAAI — BGE family (for example BGE large models on Hugging Face) are strong open-source embeddings for domain text. (See models on Hugging Face: https://huggingface.co/BAAI)
Other options

sentence-transformers — many strong, smaller embedding models (MPNet, MiniLM variants) for faster/cheaper embeddings. (https://www.sbert.net/ & https://github.com/UKPLab/sentence-transformers)
Hugging Face — primary model hub to discover and host models. (https://huggingface.co/)
Practical notes

Choose a single embedding model and use it for both JD and resume chunks. Mixing models breaks similarity.
Batch embed in pipelines (GPU if available).
Know the embedding dimension upfront (e.g., 768 or 1024) — this affects DB schema and memory planning.
Normalize vectors if using cosine similarity (some libraries do this automatically).
Tradeoffs

Larger models → better semantic nuance but higher compute & memory cost.
Smaller models → cheaper and faster but might miss seniority or domain subtlety.
4) Storage & indexing — pick and configure your vector DB
What to store
Store each chunk as a row containing:

id (primary key)
resume_id (group chunks to the resume)
text (chunk text for evidence)
embedding (float vector)
section (skills / experience / education)
metadata fields (candidate_name, skills, years_experience, location, source_file, etc.)
Recommended vector DB

Milvus — scalable, production-ready vector database with flexible indexes and partitions. (https://milvus.io/)
Other DBs to consider

FAISS — fast library for local vector search, great for prototyping. (https://github.com/facebookresearch/faiss)
Weaviate — vector DB with semantic graph features. (https://weaviate.io/)
Pinecone — fully managed vector DB if you prefer hosted service. (https://www.pinecone.io/)
Chroma — easy local vector DB for rapid prototyping. (https://www.trychroma.com/)
Index choice (high level)

HNSW (recommended for resume screening) — high accuracy/low latency, more RAM. Best when recruiter UX requires precision.
IVF_FLAT — more memory efficient at large scale, small accuracy tradeoff.
IVF_PQ — compressed storage for extreme scale (100M+ vectors) but larger accuracy cost.
Why this matters
Index choice controls the speed vs accuracy vs memory tradeoff. For hiring, missing a relevant candidate is expensive — prefer accuracy (HNSW) unless memory/scale forces another choice.

5) Retrieval strategy — hybrid (semantic + metadata)
What to do

For an incoming JD, extract explicit constraints: required skills, minimum years experience, location preferences. Simple parsing or a lightweight extractor helps.
Embed JD using the same embedding model.
Apply metadata filters in the vector DB (e.g., years_experience >= 5, location IN [US, Remote], must_have_skill = Python) to reduce candidate pool.
Run vector search for top K chunks (K = 30–100 depending on re-rank budget).
Aggregate chunk hits to resume level (we’ll cover scoring next).
Why hybrid

Vector search finds semantic matches (synonyms, inferred skills).
Metadata filtering enforces hard constraints (must-have skills, location) that vectors alone can’t guarantee.
Aggregation example

If Milvus returns 50 chunks, group by resume_id and compute resume-level score (max chunk score, or average top-N scores, or weighted by section). Max chunk score often works well: a single strong evidence chunk (e.g., “Built scalable microservices using Python & AWS”) should lift a candidate.
6) Re-ranking — the precision layer
What it is
Re-ranking means taking the top retrieved candidates (chunks or aggregated resumes) and scoring them more precisely with a more expensive model that reads JD + candidate text together.

How it works

Use a cross-encoder (a model that takes the pair (JD, chunk_text) as input and outputs a relevance score). This is slower than separate embedding comparisons but more precise because the model sees both texts jointly and reasons about fit, responsibilities, seniority, and nuance.
Model examples

Cross-encoder models on Hugging Face (e.g., cross-encoder/ms-marco-MiniLM-L-6-v2) are good mid-cost options. (https://huggingface.co/cross-encoder/ms-marco-MiniLM-L-6-v2)
For the highest precision, consider domain-adapted cross-encoders or LLM re-scoring (LLM prompts that output a fit score). LLMs are more expensive but can be more explainable if prompted carefully.
Practical tips

Re-rank only the top N retrieved items (e.g., top 50 chunks). Re-ranking everything is computationally infeasible at scale.
After re-ranking chunks, aggregate to resume level (max chunk score or weighted combination).
Optionally use short context windows for the re-rank input (e.g., top chunk + role summary) so the model reads the most relevant evidence without excessive token cost.
7) Scoring & aggregation — produce the final shortlist
Aggregation strategies

Max chunk score: take the single best chunk per resume (works well in hiring).
Average top-N: average the top 2–3 chunk scores for each resume to reward breadth.
Weighted: weight experience chunks higher than skills chunks.
Combine signals
Final ranking should combine multiple signals:

reranker_score (cross-encoder)
vector_similarity_score
business_rules_score (years experience, seniority, certs)
A linear combination with tunable weights, calibrated on labeled data, works well.
Example formula

final_score = 0.45 * reranker_score + 0.4 * max_vector_score + 0.15 * business_rules_score
Tune weights with a labeled validation set (human shortlists) and A/B tests.

8) Explainability — show recruiters why a candidate matched
What to surface

Highlighted evidence snippet(s) — the exact sentence or bullet that matched.
Which skills matched and where they were found (skills list vs experience).
A short human-readable explanation: e.g., “High match because: 5+ yrs backend APIs (Python), AWS Lambda experience, led microservices project.”
Why it matters
Recruiters need to trust the system. A score without evidence leads to low adoption. A short summary + evidence snippet increases speed and confidence.

How to produce it

Keep the original chunk text and metadata with each vector so you can show the chunk directly.
Optionally generate a 1–2 sentence human summary using an LLM (prompt: “Summarize why this resume is a match for this JD in one sentence”).
9) Evaluation & metrics — how to measure success
Key metrics

Precision@k: how many of the top-k results are relevant (very important for recruiter time-savings).
Recall@k: how many relevant candidates exist in the top-k — ensure you’re not missing gems.
MRR (Mean Reciprocal Rank): whether the best match appears near the top.
Human feedback loop: track whether recruiters progress suggested candidates to interviews or rejects them.
Evaluation process

Build a labeled test set: JDs with human-curated shortlists.
Run ablation studies: retrieval only vs retrieval + metadata vs retrieval + re-rank.
Iterate on chunking, filters, re-rank thresholds based on real user feedback.
10) Scaling & operations
Estimate vectors

Chunks per resume: ~5–20. For 1M resumes expect ~5–20M vectors. Plan storage and index memory accordingly.
Throughput & latency

Embed in batches; use GPUs for embeddings & re-ranking if low latency is required.
Cache frequent queries/embeddings (common job templates).
Use async ingestion and bulk inserts to the vector DB.
Index maintenance

Use incremental indexing for new resumes; rebuild only when you change index parameters (M, efConstruction).
Partition the collection by domain (engineering, finance) or geography (US, EU) to reduce search scope and improve latency.
Cost & infra

Embedding + re-ranking are the expensive pieces; use spot GPUs or a burstable GPU fleet.
Managed DBs (Pinecone) simplify ops; self-hosted (Milvus) gives control and cost optimization.
11) Common pitfalls & how to avoid them
Bad chunking → noisy retrieval. Fix: structure-aware chunking.
No metadata filtering → semantic noise. Fix: extract and index core metadata (skills, years, location).
Re-ranking everything → too slow / expensive. Fix: re-rank only top K.
No explainability → recruiter distrust. Fix: show evidence + short summary.

Chunking: structure-aware (custom code); fallback token windows.

Closing notes
A RAG approach converts resume screening from brittle keyword matching into human-like semantic evaluation. With structure-aware chunking, a reliable embedding model, Milvus (or similar), and a cross-encoder re-ranker, you get high recall and excellent precision — and the explainability recruiters need.
